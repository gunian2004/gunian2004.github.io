01

境外节点资源 clone 解决方法

Git · 代理配置 · 网络排查

点击展开

当 Git 通过默认网络无法拉取境外节点上的仓库时，先让系统和 Git 都明确使用 Clash 提供的代理。

设置 Clash 端口确认 Clash 正在运行，并记下 HTTP 或 Mixed 代理端口。
切换到境外节点在 Clash 中选择目标境外节点，确认节点连接正常。
开启系统代理开启系统代理，让系统应用的网络请求经过 Clash。
为 Git 配置 HTTP / HTTPS 代理使用本机代理地址，确保 Git 命令也经由 Clash 转发。
Git 代理配置示例将端口替换为 Clash 实际的 HTTP / Mixed 端口
git config --global http.proxy http://127.0.0.1:<Clash代理端口>
git config --global https.proxy http://127.0.0.1:<Clash代理端口>

配置完成后重新执行 clone。若使用 SOCKS 代理，请按对应协议调整地址前缀。

如何确认配置生效

先查看 Git 当前保存的代理地址，再使用目标仓库的 HTTPS 地址检查连通性。下方列出的是检查方法和预期现象。

01 / 查看代理配置
git config --global --get http.proxy
git config --global --get https.proxy

预期：两项都输出你配置的本机代理地址和端口。没有输出时，回到上一步检查配置。

02 / 检查仓库连通性
git ls-remote <仓库HTTPS地址>

将占位符替换为实际地址。正常时会列出可见的远程引用；认证错误需要检查仓库权限，连接超时则继续排查代理端口与节点。

不再使用代理时，撤销本次全局配置
清除 Git 全局代理
git config --global --unset-all http.proxy
git config --global --unset-all https.proxy

这会移除上述全局代理项。执行前确认其他仓库不再依赖它们。

02

项目启动前：开发规范与 AI 协作约束

规范先行 · 全系统设计 · Superpowers · AGENTS.md

点击展开

开始项目前，先调用 Superpowers 插件或技能，参照已有开发文档标准，梳理系统边界并形成可执行的开发规范，再进入编码阶段。将需求、设计、工程流程与 AI 执行约束一并明确，让后续开发与变更有据可依。

模块、字段与校验规则逐一列出模块、页面、角色、业务流程与状态流转；为每个字段明确名称、类型、必填条件、默认值、长度、取值范围、格式、联动校验、错误提示与读写权限。
前台与后台管理端设计统一样式、配色、字体、间距、图标和组件；明确表单、表格、弹窗、导航及加载、空数据、错误、禁用等状态，并定义组件复用规则。
移动端与桌面端适配分别约定布局、断点、触摸与鼠标交互、键盘操作、表格与表单展示、安全区域、浏览器兼容及无障碍要求，覆盖不同屏幕下的使用体验。
技术栈与编码规范明确前后端技术栈及版本、目录结构、命名、类型、格式化与依赖管理；统一接口契约、错误码、数据模型、日志、配置和环境隔离规则。
安全、测试与交付标准约定身份认证、权限校验、敏感信息保护、文件上传与审计要求；明确正常、异常、边界场景的测试范围，以及性能目标、验收标准、部署和回滚流程。
后续改动与变更流程按变更提出、影响分析、方案确认、文档更新、编码、测试、审查和发布的顺序推进；记录架构决策，处理接口兼容与数据迁移，确保文档和实现同步。
版本管理策略明确分支用途与命名、提交格式、合并审查、冲突处理、版本编号、发布标签和变更日志；约定紧急修复与回退方式，保留可追溯的交付记录。
AI 生成代码与执行约束通过 AGENTS.md 明确必读文档、指令优先级、允许修改的范围、编码及验证要求；禁止臆造需求、泄露密钥或擅自执行破坏性操作，对不确定项先标注并确认。
可复用提示词 / 项目启动前使用将已有文档作为参考上下文提供给 AI
在开始项目前，先调用 Superpowers 插件或技能，参照已有开发文档标准，产出一套覆盖整个系统的详尽开发规范文档，并为项目生成 AGENTS.md，用于约束和规范 AI 的执行行为。

开发规范至少覆盖：
1. 系统边界、模块清单、角色权限、页面、业务流程及状态机。
2. 各模块的每一个字段及其类型、必填条件、默认值、长度、格式、范围、联动关系、校验规则和错误提示。
3. 前台与后台管理端的样式、配色、字体、间距、组件和交互状态；前端与后端的接口契约及数据校验一致性。
4. 移动端与桌面端的布局、响应式断点、交互、兼容性及无障碍设计规范。
5. 技术栈及版本、架构、目录结构、编码、命名、类型、依赖、配置、日志和错误处理规范。
6. 安全、隐私、认证授权、审计、测试、性能、验收、部署与回滚要求。
7. 后续系统改动的提出、影响分析、确认、文档同步、开发、验证、审查和发布流程。
8. 分支、提交、合并、版本编号、发布标签、变更日志和紧急修复策略。
9. AI 生成代码的范围、约束、复核与验证要求；AGENTS.md 中的必读文档、指令优先级、执行边界和交付检查清单。

不限于上述维度。逐模块、逐页面、逐字段检查覆盖情况，为每项规则给出明确、可验证的标准。区分已确认要求、建议方案与待确认问题；不得将假设写成既定事实。发现冲突或缺失时，先列出并确认。

交付文档索引、模块规范、字段字典、设计规范、技术与编码规范、变更与版本管理规范、测试验收规范，以及 AGENTS.md，并建立相互引用，便于后续维护。若 Superpowers 不可用，明确说明，不得声称已调用。

使用时替换项目背景与参考资料；先确认规范基线，再按规范实施。提示词用于检查覆盖范围，具体规则仍需结合项目逐项确定。

落地检查

检查模块清单是否与页面、接口和字段字典对应；每项规则是否有验证方式；待确认问题是否已明确记录；AGENTS.md 是否引用有效规范，并写清 AI 的执行边界和交付要求。后续变更同时更新相关文档与实现。
